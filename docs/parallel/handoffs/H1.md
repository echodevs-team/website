## 1. Executive summary

Analytics is now **mandatory V1 scope** (`SCOPE.md` §8.4, `docs/DECISIONS.md`
A13), but provider, hosting, retention, consent, event scope and dashboard owner
remain **unapproved** (D10). This document supplies the missing decision input.

Three maintained, self-hostable products were compared against the ten required
outcomes: **Umami 3.5.0** (MIT), **Plausible Community Edition 3.2.1**
(application AGPL-3.0) and **Matomo 5.14.2** (GPL-3.0). A custom engine or custom
admin UI is unnecessary and stays out of scope.

**Conditional recommendation:** **Umami, self-hosted as a separate private
service with its own PostgreSQL database**, is the best fit for this project's
actual constraints — Node + PostgreSQL stack, small traffic, private owner-only
dashboard, and a conversion metric that must come from a **confirmed durable
inquiry write** rather than a button click. It is the only candidate whose
collection API comfortably supports a server-emitted, deduplicated conversion
event without a second database engine.

**Alternative:** **Plausible CE** if the owner prioritizes the simplest
out-of-the-box privacy posture and dashboard, and accepts a ClickHouse +
PostgreSQL stack (≥2 GB RAM) plus a client-side conversion signal with weaker
replay deduplication.

**Fallback:** **Matomo** if deep session/visitor analysis or enterprise
reporting later becomes a real requirement and a MySQL/MariaDB service is
acceptable; it is the heaviest fit here because it is PHP + MySQL, not
Node/PostgreSQL, and many advanced reports are paid plugins.

All three are license-compatible for a private, unmodified self-hosted
deployment. None is approved for use yet. "Cookieless" is a product behavior,
**not** a legal consent exemption; consent, disclosure and retention remain
owner/legal decisions.

### 2.3 Hard constraints this design must respect

1. Analytics is an **observer**, never part of the inquiry transaction.
2. No form values, names, emails, phones, descriptions, inquiry references,
   idempotency keys, raw IPs or sensitive query/fragment content in events.
3. A retry or idempotent replay must not create a second conversion.
4. Analytics failure must never delay, block, roll back or fake persistence.
5. No tracker may be enabled before the provider, consent position, retention
   and localized disclosure are approved.
6. The analytics store must not share credentials or roles with inquiry data.

## 4. Architecture comparison

The final hosting provider is unknown (E1/E1a). Both options are described as
**contracts**, not as a chosen platform.

### 4.1 Option A — self-hosted inside the eventual Echo Devs environment

**Topology**

```
Browser ──HTTPS──> Echo Next.js app (public)
                        │  pageview beacon (public collection path)
                        ▼
                  Analytics service (private hostname, authenticated dashboard)
                        │
                        ▼
                  Analytics database (separate DB/role/schema)
```

- Analytics app and database run in the same environment/region as the site, or
  on a second private instance inside the same provider account.
- Collection endpoint must be reachable from browsers; the dashboard must not be
  publicly browsable and should be restricted by authentication plus, where
  available, IP allowlist/VPN.
- Separate database, role and secrets from the inquiry database. A shared
  PostgreSQL cluster is acceptable only with a distinct database, login role and
  backup policy; it must never reuse the inquiry application role.
- Backups are part of the analytics runbook, encrypted, off-host, with a tested
  restore. They contain no inquiry payloads.
- Failure isolation: if analytics is down or slow, pageviews are dropped and the
  inquiry path is unaffected (see §5.4).

**Fit:** best with E1's likely portable Node + managed PostgreSQL target.
**Cost:** marginal if co-hosted; otherwise a small private instance.
**Risk:** co-hosting couples analytics restarts/upgrades to the site host and
must not consume the inquiry database's connection budget.

### 4.2 Option B — separately hosted analytics service

**Topology**

```
Browser ──HTTPS──> Echo site ──(CORS/allowlisted)──> Analytics origin (separate host)
                                                         │
                                                         ▼
                                                   Analytics DB (private)
```

- A dedicated small host/container platform runs the analytics app and database.
- The site origin is allowlisted; the dashboard is authentication-gated and, if
  the product supports it, restricted to an operator IP/VPN.
- TLS everywhere; HSTS after verification; no shared cookies with the site.
- Independent upgrade/restart/backup lifecycle; independent failure domain.
- Region and processor terms become a hosting/legal decision if the host is a
  third party.

**Fit:** clean isolation and simplest failure-domain story; slightly more cost
and one more thing to operate.
**Cost:** one small instance + storage + backup.

### 4.3 Option B2 — managed cloud (variant of B)

Technically valid (Umami Cloud, Plausible Cloud, Matomo Cloud) and cheapest at
very low traffic. It introduces a **third-party processor**, cross-border
transfer questions, DPA/subprocessor review and vendor retention limits. It does
not satisfy the owner's "self-hosted product" preference unless the owner
explicitly chooses it. Listed here for completeness and cost comparison, not
recommended as the default.

### 4.4 Architecture criteria

| Criterion | A: self-hosted | B: separate host | B2: managed |
|---|---|---|---|
| Deployment topology | 1 app + DB in site environment | Dedicated app + DB host | Vendor SaaS |
| Service boundaries | Shared provider, isolated DB/role | Fully isolated | Vendor boundary |
| Backup requirement | Included in site runbook | Own runbook | Vendor + export |
| Auth/admin | Product auth + network restriction | Same, easier to restrict | Vendor account, MFA |
| HTTPS/exposure | Public collection, private dashboard | Public collection, private dashboard | Public collection, vendor dashboard |
| Retention/deletion | Operator-controlled | Operator-controlled | Vendor limits + deletion request |
| Monitoring owner | Echo operator | Echo operator | Vendor + Echo operator |
| Failure isolation | Good if non-blocking | Best | Good, external dependency |
| Resource use | Marginal/shared | Predictable small | None local |
| Monthly cost `[A]` | $0–10 marginal | $5–20 + backup | $0–29+ list |
| Low-traffic suitability | High | High | High |

**Dependency note for E1/E1a/E2.** E1 must state whether the target can host a
second private service and PostgreSQL database (Option A), or only the Next app
(forcing Option B/B2). E1a must define ingress, TLS, secret storage, DB roles and
backup responsibility. E2 must provide the private staging environment where H3
can prove the tracker and conversion path. H1 does not assume any of these.

## 5. Conversion measurement proposal

### 5.1 Why a button click is not a conversion

The form's submit button can be clicked repeatedly, can fail validation, can be
rate-limited, can time out with an **uncertain** outcome, or can be retried with
the same idempotency key. Only a **confirmed durable write** is a real inquiry.
The existing client already distinguishes these states
(`success | invalid | failure | ignored`), and the database distinguishes
`replayed:false` (new row) from `replayed:true` (same row replayed). The
conversion metric must inherit that distinction.

### 5.2 Event model

| Event | Emitted by | Trigger | Allowed content | Prohibited content |
|---|---|---|---|---|
| `pageview` | Browser tracker | Each public route render | Path only; hostname allowlisted | Query string, fragment, form data |
| `contact_view` | Derived from `pageview` | Path `/{fa,en,ar}/contact` | Nothing extra | A separate duplicate event |
| `inquiry_started` *(optional, off by default)* | Browser | First focus inside the form, once per mount | Event name only | Field names/values, keystrokes, validation state |
| `inquiry_submitted` | **Server** inquiry handler | `persistInquiry` returned `replayed:false` | Fixed event name; path `/{locale}/contact`; fixed internal User-Agent | Reference, inquiry UUID, idempotency key, name, email, phone, service, timeline, description, IP, headers, payload |

**Conversion metric:** count of `inquiry_submitted` events. It represents *new
confirmed durable writes whose post-commit analytics event was delivered*. It is
therefore a **lower bound** on real inquiries and can never exceed them.

**Contact conversion rate:** `inquiry_submitted / visitors` and
`inquiry_submitted / contact_view` are both supported by the dashboard; label
which denominator is used.

### 5.3 Client-side versus server-side

| Approach | Accuracy | Attribution | Dedup on replay | PII risk | Complexity |
|---|---|---|---|---|---|
| Client event on `success` | Good for new writes | Best (same visit) | **Weak**: a `200 replayed:true` after an uncertain retry can fire again | Low if guarded | Low |
| Server event after commit, `replayed:false` only | **Exact for new writes** | Weak/noisy (server UA/IP; may count as direct/new visitor) | **Strong**: replay path never emits | Lowest (handler controls fields) | Medium |

**Recommendation (Umami):** use the **server-side** event as the authoritative
conversion signal, and do not emit a client-side conversion event. Pageviews and
the optional `inquiry_started` remain client-side for funnel context. If the
owner wants session-level attribution of conversions, H2 must explicitly accept
the extra deduplication work; it is not required by §8.4.

**If Plausible is chosen instead:** its own documentation states that server
events from webhooks/retries are unsuitable for attribution and may be dropped
as data-center traffic. The reliable Plausible design is a **client-side** event
on confirmed success with an in-memory/latched guard, accepting that an
uncertain retry that resolves as `replayed:true` could double count once. That
is a functional regression against §8.4 isolation/dedup requirements, which is
why Plausible ranks below Umami here. Matomo can do server-side tracking with
`cip`/`token_auth`, but that increases configuration and secret-handling cost.

### 5.4 Failure isolation and replay safety

Required implementation rules for H3 (D owns the hook, H owns the contract):

1. Emit **after** `persistInquiry` has committed and only when
   `saved.replayed === false`.
2. Fire-and-forget: no `await` that can delay the HTTP response; use Next.js
   `after()` or a bounded (≤1.5 s) `fetch` with `AbortController`, and swallow
   all errors.
3. Never retry the analytics call from the request path. A lost event is an
   accepted undercount, never an overcount or a blocked inquiry.
4. Never derive the event from the response body, reference or request payload.
5. If analytics configuration is absent, the emitter is a no-op.
6. Unit/integration tests inject a failing analytics transport and assert the
   inquiry still returns `201` and the row exists.

This satisfies "analytics failure must never affect persistence" and "replays
must not double count" without changing the inquiry transaction.

### 5.5 Minimization decisions

- Capture **path only** in Umami (`data-exclude-search`, `data-exclude-hash`).
  Trade-off: UTM parameters live in the query string, so excluding search also
  removes campaign attribution. If UTM tracking is required, the owner must
  approve a query allowlist (only `utm_*`) instead; do not capture arbitrary
  parameters.
- No custom event `data`/`props` objects. Fixed event-name allowlist.
- No `identify()`/Distinct ID. Visitors stay anonymous and salt-rotated.
- No form-field-derived properties, no hashed email, no inquiry reference.
- Disable vendor telemetry and external favicon lookups where configurable.

### 5.6 What the dashboard will show (and not show)

Show: pageviews/visitors over time, top paths, referrers/sources, device/browser/
OS, browser language, optional country, `inquiry_submitted` count and rate.
Do not show: individual inquiry content, contact details, per-person journeys,
cross-site behavior, or any join to the inquiry database. The dashboard is not a
lead inbox; D1's operator CLI remains the only readback path for inquiry data.

## 6. Security and privacy considerations

### 6.1 Data minimization matrix

| Data | Collected? | Note |
|---|---|---|
| Page path | Yes | Query/fragment excluded by config |
| Referrer | Yes | Browser-supplied; parse to source |
| Browser/OS/device | Yes | From User-Agent |
| Language | Yes | `navigator.language` |
| Screen size | Vendor default | Needed for device class; can be accepted |
| Approximate country | Optional | Requires IP geolocation; owner decision |
| Raw IP | Not stored as analytics field | Processed transiently for hashing/geo; ingress logs are separate |
| Inquiry payload / reference / key | **No** | Prohibited by contract and tests |
| Cookies for tracking | No (all three can run cookieless) | Site already sets a locale cookie for preference, not analytics |
| Cross-site identifiers | No | No third-party pixels or ad IDs |

### 6.2 "Cookieless" is not "consent-free"

Vendors market cookieless analytics as avoiding cookie banners. That is a
**product claim, not a legal determination**. IP-derived hashes and server logs
can still be personal data, and consent/eIDAS rules vary by jurisdiction and by
what is stored. The owner/legal decision (D6/D9/D10) must decide the lawful
basis, whether a banner is required, and the exact disclosure. H1 does not
conclude that no consent is needed.

### 6.3 Access control

- Dashboard on a private hostname; authentication required; no anonymous share
  links; no public embed.
- Strong unique password plus TOTP 2FA where supported (Umami supports and can
  enforce it; `TWO_FACTOR_ENCRYPTION_KEY` required).
- One named operator account, least privilege; owner holds admin; revocation
  procedure documented.
- Optional network restriction (VPN/IP allowlist) where the host supports it.
- `noindex`/robots deny on the analytics hostname; no links from the public site.

### 6.4 Data protection and operations

- TLS for collection and dashboard; HSTS after verification.
- Separate database, role, secret and backup from inquiry data; encrypted
  backups; no analytics data in public paths.
- Retention: delete raw events after the owner-approved period; document
  deletion method; include backups.
- Patch cadence: pinned image/tag, monthly review, prompt security updates.
  Plausible CE ≤3.2.0 had a `/storybook` RCE (`CVE-2026-8467`); 3.2.1 removes it.
  This is a concrete reason to pin and patch, not a reason to reject the product.
- Supply chain: no `latest` in production, verify image digests, review release
  notes/migrations before upgrade.
- Logging: analytics infrastructure logs may retain IPs; disclosure and
  retention must cover provider/ingress logs, not just the analytics tables.

### 6.5 Threat notes

- Public collection endpoint can be spammed; vendor bot filtering + host rate
  limits reduce noise. Analytics spam does not affect inquiry integrity.
- Dashboard compromise exposes aggregate traffic, not inquiry PII (by design).
- Server-side conversion emitter must not become an SSRF/secret-leak vector:
  fixed analytics URL from configuration, no user-controlled target, no response
  body logged.

Weighted totals: Umami `0.20·4 + 0.20·4 + 0.15·5 + 0.15·5 + 0.10·4 + 0.08·4 +
0.07·4 + 0.05·4 = 4.30`; Plausible `0.80 + 0.80 + 0.45 + 0.45 + 0.20 + 0.24 +

0.20 = 3.20`.

**False precision warning:** the 4→5 scales are qualitative. The robust
conclusion is the *ordering* and the reasons, not the second decimal. The
Plausible/Matomo gap is within scoring noise; Plausible wins on stack fit and
privacy defaults, Matomo wins on analysis depth.

### 8.3 Sensitivity

- If **hosting compatibility** is weighted 30% (likely, given an undecided host),
  Umami's lead widens.
- If **deep analysis** (funnels, cohorts, visitor profiles) becomes a real
  requirement, Matomo rises — but still needs MySQL and paid plugins.
- If the owner wants the **least configuration** for privacy, Plausible rises.
- If the owner requires **server-side confirmed conversion** without extra
  engineering, Umami is the only clean fit.

### 8.4 Main trade-offs

- **Umami:** simplest fit, but less analytical depth; self-hosted retention must
  be enforced by the operator; Node 24 compatibility is not the vendor's
  recommended LTS and needs a smoke test.
- **Plausible:** excellent privacy defaults and dashboard, but heaviest stack
  relative to need, and server-side conversion attribution is explicitly weak.
- **Matomo:** most capable, but the wrong runtime/database for this project and
  the highest operational and licensing complexity.

## 9. Recommended option and alternatives

### 9.1 Conditional recommendation

**Primary:** **Umami 3.5.0**, self-hosted, **Option B (separately hosted private
service)** with a dedicated PostgreSQL database, deployed only after D10/A3 and
E1a are approved. Rationale: matches the existing Node + PostgreSQL architecture,
covers all required metrics, supports a deduplicated server-side conversion
event, has verified 2FA and forced first-login password change, and has the
lowest footprint and cost.

If co-hosting is materially cheaper and E1a confirms a second private service is
acceptable, **Option A** is equivalent; the deciding factor is blast radius, not
the product.

### 9.2 Alternative

**Plausible CE 3.2.1**, Option B, if the owner values the simplest privacy-first
dashboard over stack fit and accepts a client-side conversion signal with weaker
replay deduplication. Budget ≥2 GB RAM and a ClickHouse backup.

### 9.3 Fallback

**Matomo 5.14.2**, separately hosted, only if deep analysis becomes a genuine
requirement and a MySQL/MariaDB service is approved. Do not adopt it merely for
feature breadth; it is the largest operational commitment here.

### 9.4 Not recommended

- Custom analytics engine or custom admin UI: out of scope and unnecessary.
- Google Analytics/Ads or third-party pixels: conflicts with minimization.
- Managed cloud as the default: adds a processor; use only with explicit owner
  approval and DPA/region review.

## 13. Remaining uncertainties

1. **Hosting target (E1/E1a):** whether a second private service and PostgreSQL
   database are available; region, TLS/ingress, secret store and backup owner.
2. **Legal/consent:** lawful basis, banner necessity and disclosure wording for
   FA/EN/AR audiences; whether IP-derived analytics data is personal data in the
   relevant jurisdictions. Vendor privacy claims are not legal advice.
3. **Umami on Node 24:** vendor recommends Node 22 LTS while the app pins Node
   24; container isolation is the safe default, but compatibility must be tested.
4. **Umami retention automation:** self-hosted data is retained indefinitely by
   default; a deletion mechanism must be implemented/operated and verified.
5. **Server-side event behavior:** how Umami's bot filtering treats a fixed
   internal User-Agent, and whether the event joins any visit; attribution may be
   Direct/None. Counts remain authoritative; attribution does not.
6. **Plausible CE specifics:** language report, 2FA, Stats API availability and
   raw export in CE are unverified; confirm before choosing Plausible.
7. **Matomo 6:** beta timeline and whether MySQL 8+/MariaDB 10.6+ is acceptable;
   premium plugin need and cost.
8. **UTM trade-off:** excluding query strings removes campaign attribution; an
   allowlist is the only safe alternative and needs owner approval.
9. **Managed pricing/terms:** list prices and retention are current at access
   date but subject to change; DPA/subprocessors/region unverified.
10. **Self-host cost figures** are market estimates, not quotes, and depend on the
    eventual provider.
11. **Traffic forecast:** no real analytics baseline exists, so tier/capacity
    sizing is an assumption for a small business site.
