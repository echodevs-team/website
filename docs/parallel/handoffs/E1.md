## 1. Executive summary

The application is a **single long-lived Next.js Node process** with a
**loopback-only** listener (`next start --hostname 127.0.0.1`), a **private
PostgreSQL 17+** database reached through a small pool, and a **fail-closed**
inquiry endpoint that trusts client identity only when an **HMAC-signed ingress
envelope** (`x-echo-client-ip/time/signature`) is present. D1 converted that into
19 HARD host requirements (HC-R/D/N), plus operator, logging, backup and privacy
requirements (HC-O/L/B/P).

Two consequences dominate the assessment and neither is a provider marketing
question:

1. **The signed ingress is engineering the project must supply.** No evaluated
   platform injects a per-request HMAC over `time\nip\nPOST\n/api/inquiries\nkey`.
   The ingress signer is therefore a component E1a/E2 must design, implement and
   test whatever provider is chosen. That single fact removes most of the
   "just use a managed platform" advantage and makes a contestable, auditable
   reverse proxy mandatory.
2. **PostgreSQL ≥17 plus TLS, distinct least-privilege roles, off-host backup and
   PITR are HARD.** They are cheap from a managed database and are real ongoing
   work on a self-managed one — but a managed database cannot serve the existing
   operator CLI, which is **project-local Unix-socket only** until D2 adds a TLS
   path (D1-G08).

**Recommendation (§7):** *Option B — one small VPS running the Next.js app,
ingress signer, TLS and the private analytics service, with a managed
PostgreSQL 17/18 in the same country/region.* It clears every HARD item that is
in engineering's control, keeps the self-hosted analytics requirement cheap
(one extra container, no extra bill), and confines the one unavoidable custom
security component to a host the project fully controls. *Option A* (all-in-one
VPS with self-managed PostgreSQL) is the budget fallback at roughly two-thirds
the cost but adds unbuilt production database work. *Option C* (managed
container platform + managed PostgreSQL) is **not recommended until D accepts a
contract revision**, because it cannot meet HC-N5 (per-IP edge volumetric
limits), cannot sign HC-N3 at the platform edge, and on the reviewed product has
an internal-TLS limitation that conflicts with HC-D3.

Nothing here selects a provider, region, budget, domain or analytics product.
A5/D4, A6 and D10 remain owner decisions.

## 4. Options considered

### Option A — single small VPS, self-managed PostgreSQL

One Hetzner-class VPS (2 vCPU / 4 GB / 80 GB NVMe) running, in containers or
systemd units: Caddy or nginx for TLS/limits, a signing proxy that produces the
HMAC envelope, the Next.js app on loopback, PostgreSQL 18 with a private socket
and TLS for the few remaining remote paths, plus the analytics container and its
own database/role. Provider snapshots plus a nightly logical dump to storage-box
or S3-compatible object storage; WAL archiving for PITR is added later or
accepted as a documented gap with owner-approved RPO.

**Best when** the owner wants minimum recurring cost, full control of the
ingress contract, and the existing Unix-socket operator CLI to keep working
unchanged; **worst when** nobody will own OS patching, PostgreSQL upgrades, TLS
renewal and backup verification.

### Option B — small VPS for the app, managed PostgreSQL (recommended)

Same VPS role as Option A for TLS, signing ingress, app and analytics, but the
inquiry database is a managed PostgreSQL 17/18 instance in the same country
(e.g. Hetzner Nuremberg/Falkenstein app + DigitalOcean Frankfurt database), with
provider daily backups, 7-day PITR, disk encryption, TLS with
`sslmode=verify-full` and CA, and trusted-source/allow-list rules limiting
inbound connections to the VPS and approved operator addresses.

**Best when** the owner accepts roughly +USD 15/month to remove the highest-risk
database work (PITR, restore drill, encryption at rest, version upgrades) while
keeping full control of the ingress. **Cost:** the existing operator CLI cannot
read a remote database, so D2's TLS operator path (D1-G08, 4–6 h, already
budgeted) becomes a hard prerequisite for the first real lead readback.

### Option C — managed container platform + managed PostgreSQL

Render (or Railway) web service running the app image with an in-container
proxy that terminates nothing but re-signs and forwards to a loopback-bound
`next start`, plus the provider's managed PostgreSQL and a second service for
analytics.

**Best when** the owner wants patching, deploys and TLS handled by a vendor.
**Not recommended now:** the platform edge cannot sign HC-N3, no per-IP
edge rate/body limits are documented (HC-N5), the reviewed provider's internal
database URL supports only `sslmode=require` with self-signed certificates
(conflicts with HC-D3's CA verification), and every vendor becomes an
additional processor to disclose. It also roughly doubles-to-triples cost
because analytics needs its own service and database.

### Rejected without further assessment

- **Vercel + Neon/managed Postgres:** Vercel Functions are request-scoped, so
  HC-R1 ("long-lived Node process") and HC-R6/R4 (persistent bounded pool,
  loopback-only backend) fail; the repo's `pg` pool would be recreated per
  instance. Serverless is a viable product for static marketing, not for this
  D1 contract.
- **Static-only hosting anywhere:** fails C1–C3 outright (no durable inquiry).
- **Kubernetes, service mesh, microservices, queue/broker:** no requirement in
  SCOPE or D1 needs them; they multiply cost and operational surface for one
  small app and one database.
- **Running production on the `agent-lab` development VM:** prohibited by SCOPE
  §8.1 and this workspace's isolation rules.

### 6.3 Target pipeline shape (proposal only — not implemented by E1)

1. **verify** (exists, keep): install → lint → typecheck → unit → `qa:validate`
   → `verify:reference` → build.
2. **database** (new): disposable PostgreSQL 18, `migrate` + `migrate --verify`,
   `test:inquiries -- --http`, log-privacy assertion. Two implementation routes:
   keep the embedded-cluster runner (fastest, no service container, but a
   beta `@embedded-postgres/linux-x64` devDependency — verify it works under
   `--ignore-scripts` in a hosted runner), or add a `services: postgres:18`
   container and let the runner accept an external disposable URL (code change
   in D-owned scripts, needs a D-lane review).
3. **artifact** (new): build once, produce an immutable image or standalone
   bundle, record commit SHA + digest, optionally an SBOM.
4. **deploy staging** (new): protected `staging` environment, synthetic-only
   data, `INQUIRIES_ENABLED=false` until D3, noindex, migration `--verify` →
   apply → restart with drain → health check → smoke.
5. **deploy production** (new, separate authorization): protected `production`
   environment whose required reviewer is the G2 approver; same steps, previous
   digest retained for rollback; post-deploy smoke and an explicit
   `INQUIRIES_ENABLED` / `ECHO_PUBLIC_INDEXING` flip that is never automatic.
6. **Release record**: commit, image digest, migration versions applied,
   rollback digest, backup point, RPO/RTO — the ECHO-706 content.

Note on GitHub plan: environment protection with required reviewers and
environment-scoped secrets are not available on every GitHub plan; the owner
must confirm the plan before E4 relies on them.

## 7. Recommended architecture (conditional)

**Primary: Option B.** One 4 GB VPS in the chosen country running:

- Caddy (TLS, HTTP→HTTPS, HSTS after verification, header/read/idle timeouts,
  body cap, per-IP rate limit) → **signing proxy** (strips inbound
  `x-echo-client-*`, derives the peer IP from the socket or a trust-checked hop,
  computes the HMAC with `INQUIRY_PROXY_SECRET`, sets the three envelope
  headers) → Next.js bound to `127.0.0.1:3000`.
- The analytics service (Umami as a candidate only) in its own container with
  its own database and role, memory/CPU-limited so it cannot starve intake.
- Managed PostgreSQL 17/18 in the same country, private by trusted sources,
  `sslmode=verify-full`, daily backup + 7-day PITR, separate roles for app,
  migration, read, erase, backup and restore.
- Off-host encrypted logical backups as a supplement, with an independent key
  custodian; one verified restore drill before intake opens.

**Fallback: Option A** if the owner sets a hard budget near USD 25/month or
requires that the database never leaves project-controlled infrastructure. It
keeps the existing operator CLI working as-is, but adds production PostgreSQL
hardening (TLS, `pg_hba`, roles, WAL archiving/PITR, upgrade cadence) to E/D
scope and must be scheduled as real work, not assumed.

**Conditional on owner decisions:** provider and region (A5/D4/D9), acceptable
monthly ceiling, domain/DNS/TLS control (A6), operator identities and MFA (D5),
retention/RPO/RTO and processor disclosure (D6/D9), analytics provider (D10),
and explicit authorization to provision anything at all (E1a/E2).

**Ingress mechanism** (E1a decision, short spike recommended): a small Node
signing proxy is the default candidate because it reuses the existing runtime,
`node:crypto` and the repository's HMAC tests; nginx+`njs`, OpenResty/Lua or an
edge Worker are alternatives whose HMAC capability, trust chain and processor
implications must be verified before selection. If a CDN/WAF is placed in
front, it must pass the true client IP over an authenticated hop and the signer
must verify that hop — otherwise the envelope is meaningless. This is the one
part of the design that no provider supplies and that must be reviewed by the
Security & Operator Readiness role.
