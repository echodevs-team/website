## 1. Executive summary

The inquiry vertical slice is **substantially implemented, internally consistent
and defensively coded** — materially more than a prototype. Verified in source:
fail-closed configuration, strict shared validation mirrored by database
constraints, commit-before-success persistence, PostgreSQL-enforced idempotency
with an advisory lock, bounded shared rate limits, an explicit signed-proxy
identity contract, NOLOGIN capability groups, replay-safe single-record erasure,
encrypted bounded snapshots, checksummed migrations and a disposable-database
test runner. P2-B2 records a 40-test PostgreSQL/HTTP/DOM fixture run; the four
integration files currently contain 37 `it` cases covering the same behaviours.

It is **not production-operable**. The system is a *development-complete* slice:
its trusted ingress exists only as a written contract, its operator tooling
refuses anything except this checkout's private Unix socket, no operator identity
or membership exists, no retention/purge policy or mechanism exists, backup is a
1,000-row local snapshot with no PITR/off-host/key-custody/RPO/RTO or target-infra
restore drill, and there is no application logging, health endpoint or alerting.
The release-critical PostgreSQL QA case has **never been recorded** and is not run
in CI.

22 gaps are recorded: **6 BLOCKER, 12 IMPORTANT, 4 OPTIONAL**. The blockers are
not missing application features; they are the production boundary (ingress,
managed database access, operator identities, retention, backup/restore) plus the
absence of edge volumetric controls. Until those are closed and A3/D4/D5/D6/D9
are answered, enabling real-user intake would violate the SCOPE §10 never-launch
conditions ("no operational way to retrieve leads", "no rollback/backup plan",
missing TLS and host controls).

D1's deliverable is therefore the **requirements contract** a host must satisfy
(§4), so E1a can select a target without guessing, and D2 can implement only the
approved remainder. No provider, region, budget, retention period, operator or
legal position is proposed here; those remain owner decisions (§6).

## 2. Existing architecture and verified capabilities

### 2.1 Request path as implemented

1. `POST /api/inquiries` — the only exported method
   ([`src/app/api/inquiries/route.ts`](../../../src/app/api/inquiries/route.ts)).
   Config is read per request, and the API is disabled unless
   `INQUIRIES_ENABLED === "true"`.
2. Fail-closed configuration: origin must be a bare `http`/`https` origin, the
   digest secret must be ≥32 characters, otherwise a generic 503
   ([`handler.ts:41-44`](../../../src/lib/inquiries/handler.ts)).
3. Exact `Origin` equality (missing or foreign → 403) and `Sec-Fetch-Site:
   cross-site` rejection; JSON only with optional `charset=utf-8`; any
   `Content-Encoding` → 415; UUID `Idempotency-Key` → 400
   ([`handler.ts:44-47`](../../../src/lib/inquiries/handler.ts)).
4. Streamed body read with a 32 KiB cap (Content-Length pre-check *and* counted
   stream) and a 5 s deadline; invalid UTF-8/JSON → 400/408/413
   ([`handler.ts:9-33`](../../../src/lib/inquiries/handler.ts)).
5. Strict Zod schema: unknown keys rejected, name 2–120, description 20–5000 with
   control-character rejection, email/phone alternatives, Unicode digit
   normalization, allowlisted `service`/`budget`/`locale`/`sourcePage`, empty
   honeypot ([`src/lib/validation/inquiry.ts:12-26`](../../../src/lib/validation/inquiry.ts)).
   Errors are reduced to allowlisted field names plus `invalid`/`required`.
6. Network identity: `loopback` (development only, headers ignored) or
   `signed-proxy` (HMAC over `time\nip\nPOST\n/api/inquiries\nkey`, ±30 s,
   constant-time compare), IPv4-mapped IPv6 unified, native IPv6 grouped by /64
   ([`network.ts:30-47`](../../../src/lib/inquiries/network.ts)).
7. Persistence: HMAC-SHA256 payload digest, shared global and per-network attempt
   buckets consumed *before* the write, per-key advisory lock, replay when the
   same key+digest is active (200), 409 on key reuse with a different payload,
   insert + 24 h replay row in one transaction, success only after `COMMIT`
   ([`store.ts:8-42`](../../../src/lib/inquiries/store.ts),
   [`limits.ts:6-31`](../../../src/lib/inquiries/limits.ts)).
8. Database: constrained tables, partial indexes, 24 h replay metadata with
   `ON DELETE CASCADE`, 10 min network buckets, one fixed global bucket
   ([`001_inquiries.sql`](../../../db/migrations/001_inquiries.sql),
   [`002_network_limits.sql`](../../../db/migrations/002_network_limits.sql)).
9. Operator path: `list`/`show`/`delete`/`backup`/`restore`/`keygen`, dedicated
   credentials, PII acknowledgement, private 0600 non-overwritten files, keyset
   pagination, AES-256-GCM snapshots with migration/row/size checks
   ([`scripts/inquiry-ops.mjs`](../../../scripts/inquiry-ops.mjs)).

### 2.3 Deliberate boundaries (not gaps)

- No public read endpoint, no GET/PUT/DELETE handler; GET is 405 (verified by
  `tests/integration/inquiry-http.test.ts:43-46` and `scripts/smoke-http.mjs:380-384`).
- No CORS headers; same-origin only.
- No HTML rendering of submitted text; only the static theme-init script uses
  `dangerouslySetInnerHTML`.
- No queue, Redis or notification dependency; `pg` and Node crypto only.
- No raw IP storage in the application; network identities are domain-separated
  HMACs. Ingress/provider logs may still contain IPs (§4.7, §6).
- No automatic business deletion: intentional until D6 is answered.
- No operator/admin web UI: required by SCOPE §7.2.

| HC-N1 | TLS 1.2+ (1.3 preferred) with a valid certificate for the approved origin; HTTP→HTTPS redirect. HSTS only after TLS and all subresources are verified. | HARD |
| HC-N2 | Ingress preserves the browser `Origin` byte-for-byte; it must not rewrite it to an internal hostname. Cross-site and missing-Origin requests must still reach the app for its 403 (do not "fix" them at the edge). | HARD |
| HC-N3 | Ingress derives the client IP only from the socket or a trust-checked upstream chain, **strips every incoming `x-echo-client-*` header**, and injects `x-echo-client-ip`, `x-echo-client-time` (13-digit ms, ±30 s) and `x-echo-client-signature` = hex HMAC-SHA256 over `<time>\n<ip>\nPOST\n/api/inquiries\n<lowercase UUID key>` using an independent `INQUIRY_PROXY_SECRET` shared only with the app. | HARD |
| HC-N4 | The application runtime is not reachable from the public internet; ingress is the only path (private network/security group, mTLS or equivalent). | HARD |
| HC-N5 | Edge request limits: body ≤32 KiB (reject before buffering), header/read/idle timeouts, per-IP connection and request-rate limits, concurrency cap, and DDoS/WAF protection. These are not optional because the app deliberately has no per-IP pre-validation counter. | HARD |
| HC-N6 | No request/response body logging at the edge; no caching of `/api/inquiries`; no compression accepted or added for that route. | HARD |
| HC-N7 | A request identifier is preserved or added at the edge and returned to the client in a non-sensitive header (app already emits `X-Request-ID`); it must not contain PII. | HARD |

Run on an isolated staging environment with synthetic data only; each item must
produce recorded evidence, and none may be inferred from unit tests.

| ID | Check | Expected result |
|---|---|---|

| HC-V2 | Exact Origin | Correct Origin accepted; missing/foreign → 403; `Sec-Fetch-Site: cross-site` → 403 |
| HC-V3 | Signed envelope | Valid → 201; missing/forged/stale (>30 s) → 503; direct backend request → 503 and no row |
| HC-V4 | Body limits | >32 KiB (Content-Length and chunked) → 413; stalled body → 408 within ~5 s |
| HC-V5 | Media type | Non-JSON or compressed body → 415 |
| HC-V6 | Idempotency | Same key+payload → 200 with the same reference; changed payload → 409; no duplicate rows |
| HC-V7 | Rate limits | 6th attempt from one network → 429 with `Retry-After: 600`; global cap behaves; recovery after the window |
| HC-V8 | DB failure | Revoked permission/stopped DB → 503, zero rows, no internals; restored permission works |
| HC-V9 | Operator readback | Separate login lists/shows one record; app credential and anonymous access denied; no PII in stdout |
| HC-V10 | Erasure | Dry run; apply with confirmation; active replay refused; dependent metadata cascades; no payload in output |
| HC-V11 | Backup/restore | Snapshot restores into a fresh empty target with identical counts/Unicode; wrong key/migration mismatch fail closed |
| HC-V12 | Cleanup | Scheduler removes only expired replay/network rows; inquiries retained; failure rolls back and alerts |
| HC-V13 | Log redaction | Request id present; no payload/IP/parameters/cookies in app, edge or DB logs |

## 11. Uncertainties and limitations

- **No real ingress, TLS, managed database, operator login or clock-skew test was
  performed or available.** Every statement about those paths is a requirement
  derived from source and documentation, not observed behaviour.
- **Abuse/capacity is unmeasured.** The 30/10 min global and 5/10 min network caps
  are untuned; real traffic, NAT behaviour, IPv6 /64 grouping and edge limits need
  measurement in staging (D3/D4). No claim is made that the current caps suit this
  business.
- **Integration evidence is stale-by-definition.** The P2 reports describe a
  disposable local PostgreSQL 18.6 fixture; the embedded package is a
  development-only distribution and is not installed in this audit worktree. No
  current, clean-tree QA record exists for persistence, roles or recovery.
- **QA freshness caveats.** PASS records for build/unit/http are not tied to source
  changes, and the PostgreSQL case has a prerequisite mismatch (§2.4). Treat the
  14 PASS snapshot as an infrastructure/UI baseline, not inquiry proof.
- **Provider version risk.** `MAINTAIN` requires PostgreSQL 17+; a provider
  offering 15/16 would fail provisioning until the grant is reviewed (D2).
- **Replay-digest coupling.** The HMAC covers `JSON.stringify` of the normalized
  Zod output. A future schema key/order change, or rotating
  `INQUIRY_DIGEST_SECRET` inside a 24 h window, turns a legitimate retry into a
  409 and resets network buckets. The runbook must require deploying schema
  changes outside active replay windows (or version the digest).
- **Erasure is not deletion everywhere.** Live-row deletion cannot remove prior
  snapshots, exports or provider logs; the 24 h active-replay refusal has no
  approved urgent protocol. Only D6 can settle this.
- **Restore semantics depend on secrets not in the snapshot.** Replay metadata
  restores with original expiry, but resuming replay requires the original digest
  secret; roles, passwords and configuration are never in the snapshot.
- **No penetration test, DAST, dependency audit or load test** was run. This is a
  design/code audit, not a security certification.
- **Legal/compliance is out of scope.** No claim is made about GDPR/other
  regimes; D6/D9 and the Privacy & Legal Approver decide.
- **Analytics (D10/H3) is untouched.** The conversion-hook boundary is specified
  in §4.8/§7 but no provider, consent or event schema is implied.
- **Effort estimates** assume an experienced developer familiar with the code and
  exclude owner response time, provider provisioning delays and browser/manual
  reviewers.
