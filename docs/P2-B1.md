## Retry semantics

`InquirySubmission` generates a UUID per logical attempt after client validation, freezes its normalized payload, and applies a **15s** request/response-read deadline with cancellation. A lost acknowledgement after COMMIT shows uncertainty, never success. Retry uses the same key/data even if changed raw values are passed accidentally.

An initial authoritative 400/403/413/415/429 is a known rejection, so correction can start a fresh key. After any earlier uncertainty, those later rejections **do not** establish that the earlier write failed; the original snapshot/key stay locked. A 409 does not rotate/resend automatically: a warning and explicit “separate inquiry” action are required. Success prevents resubmission until explicit new intent. Retry-After is honored with a bounded, localized wait display; the class also guards attempts before that deadline. Countdown runs only while waiting, no animation.

The client refuses automatic retry after **23h** from first attempt, conservatively inside the backend's 24h replay window. It does not silently rotate an expired uncertain key. An operator verification/recovery workflow is still P2-B2. Different keys can intentionally create distinct records; this is bounded idempotency, not permanent content deduplication.

## Network identity / deployment assumptions

Next Route Handlers do not expose a verified socket peer. Never infer it from `Host`, `Forwarded`, `X-Forwarded-For`, `X-Real-IP` or an unsigned custom header. `INQUIRY_NETWORK_MODE` is explicit; missing/invalid identity configuration fails closed with safe 503 **before DB writes**.

### `loopback` — private development/test only

All submissions share the `127.0.0.1` network bucket; forwarding headers are ignored, not interpreted. Configured origin and internal request URL must both be loopback with matching protocol/port. Internal loopback aliases are accepted because Next normalizes `127.0.0.1` to `localhost`; browser Origin enforcement remains an **exact string match** to the configured origin.

This mode assumes Next is actually bound to loopback (as repository scripts do). A loopback-looking Host/URL does **not** prove the peer address or secure a publicly bound listener. **Never use loopback mode behind a public ingress/listener.** No host/listener changes were made in this batch.

### `signed-proxy` — implemented contract, NOT verified deployment integration

Requires independent random `INQUIRY_PROXY_SECRET` (>=32 chars), held only by app and trusted ingress. Trusted ingress must determine the real client IP from its socket/trust-checked upstream chain, strip all incoming `x-echo-client-*` headers, and inject:

- `x-echo-client-ip`: bare IPv4/IPv6 (no ports, brackets, zone or list)
- `x-echo-client-time`: 13-digit Unix milliseconds, within ±30s
- `x-echo-client-signature`: lowercase hex HMAC-SHA256 of the exact UTF-8 string:

```text
<time>\n<ip>\nPOST\n/api/inquiries\n<lowercase Idempotency-Key UUID>
```

Here `\n` denotes a newline, not two literal characters. App compares MACs in constant time, checks freshness/key binding, then canonicalizes the IP. IPv4-mapped IPv6 joins the IPv4 bucket. Native IPv6 uses **/64** to bound privacy-address rotation; IPv4 uses a full address. Shared NAT and /64 group limits may affect legitimate users; traffic tuning is not claimed.

App/edge clocks must be synchronized. The signing secret and envelope must never be exposed to client JS, responses, analytics or logs; proxy request/parameter logging needs review. Restrict backend access and verify ingress overwrite/signing from actual socket data. No proxy, external service, secret provisioning, routing or firewall was configured here. Generic forwarded headers remain unused in both modes. The signed fixture tests prove code behavior, **not** a real provider's trust chain.

## Atomic limits and temporary retention

- Retained shared global cap: **30 attempts / 10min**, saturating at 31.
- Added shared network cap: **5 attempts / 10min**, saturating at 6, atomic PostgreSQL UPSERT. Replays/conflicts and valid attempts whose later write fails consume quota; inquiry rollback does not restore quota.
- Network table stores domain-separated HMAC identities, never raw IPs, with expiry index. Attempts over the global cap cannot allocate network rows. At most two adjacent global windows' network allocations overlap (up to about 60 active buckets); expired rows are removed opportunistically in batches capped at 200.
- Replay metadata expires at 24h; bounded opportunistic expired-replay cleanup also runs on global-admitted valid requests. Inquiry records are not deleted by this cleanup. Expired metadata is never treated as a valid replay even if maintenance has not run.
- `db:cleanup` now removes expired replay **and network** rows, logging counts only. Tested with disposable data. With no traffic, physical removal requires this command; a production scheduled invocation and inquiry retention/deletion policy remain unconfigured P2-B2/hosting gates. No cron/service was installed.
- 429 has no payload or storage details and conservative `Retry-After: 600`; the UI displays guidance and blocks early retries. Global/database failure is fail-closed 503. No Redis, CAPTCHA or new dependency.

Strict validation, 32KiB streamed body cap, 5s body deadline, exact Origin, JSON-only/no content encoding and honeypot rejection are retained. The empty honeypot is only a cheap signal, not a security boundary. Application-side counters do not replace ingress connection/body/read-timeout/concurrency limits against floods; those limits must be selected and verified for the actual host.

```sh
npm run db:dev
# Separate terminal; explicitly enable SYNTHETIC LOCAL testing only:
INQUIRIES_ENABLED=true npm run dev:inquiries
```

Open **http://127.0.0.1:3000/fa**, `/en` or `/ar` (matching exact configured Origin). Helper-generated config retains `INQUIRIES_ENABLED=false` and `INQUIRY_NETWORK_MODE=loopback` by default, so a normal unconfigured preview cannot silently start collecting data. The form is functional after hydration; an unavailable/misconfigured API yields a retained-draft error, not fake success. Do not use real customer data on this VM.
